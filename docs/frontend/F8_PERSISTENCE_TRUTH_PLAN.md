## 1. Current Database Architecture & Baseline Analysis

### 1.1 Overview
DataFlowX is a modular monolith built with **Java 21** and **Spring Boot 3.2.0**. Persistence is managed through **Spring Data JPA** and **Hibernate ORM 6.3.1.Final**. 

At present, database lifecycle management is divided across two conflicting paradigms:
1. **Production & Runtime Target:** PostgreSQL 15 (`postgres:15-alpine` in `docker-compose.yml`).
2. **Integration Test Target:** In-memory H2 Database (`jdbc:h2:mem:dataflowx;MODE=PostgreSQL;DATABASE_TO_LOWER=TRUE;DB_CLOSE_DELAY=-1`).

### 1.2 The Core Problem Statement
* **No Database Migration Tooling:** There is no Flyway or Liquibase dependency in `pom.xml`.
* **Empty PostgreSQL Bootstrapping Failure:** In `application-prod.properties`, Hibernate is configured with `spring.jpa.hibernate.ddl-auto=${JPA_DDL_AUTO:validate}`. Because no migration engine exists to generate tables prior to Hibernate initialization, booting a production instance against a fresh, empty PostgreSQL database **fails immediately** with `SchemaManagementException: Schema-validation: missing table [users]`.
* **Dual-Dialect Risk (H2 vs. PostgreSQL):** All 8 Spring Boot integration test suites run against in-memory H2. H2 in `MODE=PostgreSQL` emulates PostgreSQL syntax but diverges in fundamental behaviors:
  * Foreign key violation handling, error codes, and constraint diagnostic messaging.
  * Identity column generation vs. sequence emulation.
  * Timestamp precision (`Instant` mapping to `TIMESTAMP(6) WITH TIME ZONE` vs. H2 timestamps).
  * Case folding (`DATABASE_TO_LOWER=TRUE` in H2 vs. PostgreSQL standard lowercase folding).
* **Target Architecture:**
  * **Schema Definition:** Database migrations managed exclusively via Flyway SQL scripts.
  * **Hibernate Role:** Strict schema consumer (`spring.jpa.hibernate.ddl-auto=validate`) across all environments.
  * **Testing Truth:** Real PostgreSQL via Testcontainers for all integration tests verifying database interactions.

## 2. Verified Entity & Schema Inventory

The repository contains exactly three JPA entities: `User`, `Dataset`, and `Job`. There are no bidirectional `@OneToMany` collections, no `@MappedSuperclass`, no `@Embeddable`, and no custom `@Converter` classes.

### 2.1 Entity Details

#### A. User (`com.dataflowx.auth.entity.User`)
* **Table:** `users` (`@Table(name = "users")`)
* **Primary Key:** `id` (`Long`), generated via `GenerationType.IDENTITY`.
* **Columns:**
  * `id`: `BIGINT GENERATED BY DEFAULT AS IDENTITY` — Primary Key, NOT NULL.
  * `username`: `VARCHAR(100)` — NOT NULL.
  * `email`: `VARCHAR(254)` — NOT NULL, UNIQUE (unique constraint: `uk_users_email`).
  * `password`: `VARCHAR(255)` — NOT NULL (BCrypt hashed string).
  * `role`: `VARCHAR(20)` — NOT NULL, stored as String (`EnumType.STRING`), values: `USER`, `ADMIN`.
  * `created_at`: `TIMESTAMP(6) WITH TIME ZONE` — NOT NULL, updatable = false, set in `@PrePersist`.
  * `updated_at`: `TIMESTAMP(6) WITH TIME ZONE` — NOT NULL, set in `@PrePersist` and `@PreUpdate`.
* **Relationships:** None defined on the entity (referenced by `Dataset.owner`).

#### B. Dataset (`com.dataflowx.dataset.entity.Dataset`)
* **Table:** `datasets` (`@Table(name = "datasets", indexes = { @Index(name = "idx_datasets_owner_id", columnList = "owner_id") })`)
* **Primary Key:** `id` (`Long`), generated via `GenerationType.IDENTITY`.
* **Columns:**
  * `id`: `BIGINT GENERATED BY DEFAULT AS IDENTITY` — Primary Key, NOT NULL.
  * `name`: `VARCHAR(200)` — NOT NULL.
  * `description`: `VARCHAR(2000)` — NULLABLE (optional field).
  * `owner_id`: `BIGINT` — NOT NULL, Foreign Key referencing `users(id)`.
  * `status`: `VARCHAR(20)` — NOT NULL, stored as String (`EnumType.STRING`), values: `ACTIVE`, `ARCHIVED`. Default: `ACTIVE`.
  * `created_at`: `TIMESTAMP(6) WITH TIME ZONE` — NOT NULL, updatable = false, set in `@PrePersist`.
  * `updated_at`: `TIMESTAMP(6) WITH TIME ZONE` — NOT NULL, set in `@PrePersist` and `@PreUpdate`.
* **Relationships:**
  * `@ManyToOne(fetch = FetchType.LAZY, optional = false)` to `User` via `@JoinColumn(name = "owner_id", nullable = false)`.
  * No cascade options configured (no `CascadeType.ALL` or `CascadeType.REMOVE`).
  * No orphan removal (`orphanRemoval = false`).
* **Indexes:** `idx_datasets_owner_id` on `owner_id`.

#### C. Job (`com.dataflowx.job.entity.Job`)
* **Table:** `jobs` (`@Table(name = "jobs", indexes = { @Index(name = "idx_jobs_dataset_id", columnList = "dataset_id"), @Index(name = "idx_jobs_status", columnList = "status"), @Index(name = "idx_jobs_submitted_at", columnList = "submittedAt") })`)
* **Primary Key:** `id` (`Long`), generated via `GenerationType.IDENTITY`.
* **Columns:**
  * `id`: `BIGINT GENERATED BY DEFAULT AS IDENTITY` — Primary Key, NOT NULL.
  * `dataset_id`: `BIGINT` — NOT NULL, Foreign Key referencing `datasets(id)`.
  * `status`: `VARCHAR(20)` — NOT NULL, stored as String (`EnumType.STRING`), values: `PENDING`, `RUNNING`, `COMPLETED`, `FAILED`. Default: `PENDING`.
  * `progress`: `INTEGER` — NOT NULL, Bean Validation `@Min(0)` and `@Max(100)`. Default: 0.
  * `submitted_at`: `TIMESTAMP(6) WITH TIME ZONE` — NOT NULL, updatable = false, set in `@PrePersist`.
  * `started_at`: `TIMESTAMP(6) WITH TIME ZONE` — NULLABLE, set on transition to `RUNNING`.
  * `completed_at`: `TIMESTAMP(6) WITH TIME ZONE` — NULLABLE, set on transition to `COMPLETED` or `FAILED`.
  * `error_message`: `VARCHAR(2000)` — NULLABLE, set on transition to `FAILED`.
* **Relationships:**
  * `@ManyToOne(fetch = FetchType.LAZY, optional = false)` to `Dataset` via `@JoinColumn(name = "dataset_id", nullable = false)`.
  * No cascade options configured.
* **Indexes:**
  * `idx_jobs_dataset_id` on `dataset_id`.
  * `idx_jobs_status` on `status`.
  * `idx_jobs_submitted_at` on `submitted_at` (derived from `columnList = "submittedAt"` by Spring naming strategy).

```sql
-- =============================================================================
-- DataFlowX Baseline Schema Migration
-- Version: V1__initial_schema.sql
-- Database: PostgreSQL 15+
-- =============================================================================

-- 1. Table: users
CREATE TABLE users (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    username VARCHAR(100) NOT NULL,
    email VARCHAR(254) NOT NULL,
    password VARCHAR(255) NOT NULL,
    role VARCHAR(20) NOT NULL,
    created_at TIMESTAMPTZ(6) NOT NULL,
    updated_at TIMESTAMPTZ(6) NOT NULL,
    CONSTRAINT uk_users_email UNIQUE (email)
);

-- 2. Table: datasets
CREATE TABLE datasets (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(200) NOT NULL,
    description VARCHAR(2000),
    owner_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    created_at TIMESTAMPTZ(6) NOT NULL,
    updated_at TIMESTAMPTZ(6) NOT NULL,
    CONSTRAINT fk_datasets_owner_id FOREIGN KEY (owner_id) REFERENCES users (id)
);

CREATE INDEX idx_datasets_owner_id ON datasets (owner_id);

-- 3. Table: jobs
CREATE TABLE jobs (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    dataset_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    progress INTEGER NOT NULL,
    submitted_at TIMESTAMPTZ(6) NOT NULL,
    started_at TIMESTAMPTZ(6),
    completed_at TIMESTAMPTZ(6),
    error_message VARCHAR(2000),
    CONSTRAINT fk_jobs_dataset_id FOREIGN KEY (dataset_id) REFERENCES datasets (id),
    CONSTRAINT chk_jobs_progress CHECK (progress >= 0 AND progress <= 100)
);

CREATE INDEX idx_jobs_dataset_id ON jobs (dataset_id);
CREATE INDEX idx_jobs_status ON jobs (status);
CREATE INDEX idx_jobs_submitted_at ON jobs (submitted_at);
```

### 6.2 Container Lifecycle: Shared Singleton Pattern
```java
package com.dataflowx.test;

import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.testcontainers.service.connection.ServiceConnection;
import org.springframework.test.context.ActiveProfiles;
import org.testcontainers.containers.PostgreSQLContainer;
import org.testcontainers.junit.jupiter.Container;

@SpringBootTest
@ActiveProfiles("test")
public abstract class AbstractIntegrationTest {

    @Container
    @ServiceConnection
    protected static final PostgreSQLContainer<?> postgres = 
        new PostgreSQLContainer<>("postgres:15-alpine")
            .withDatabaseName("dataflowx_test")
            .withUsername("test")
            .withPassword("test");

    static {
        postgres.start();
    }
}
```

## 9. Migration Risks & Mitigation Matrix

| Risk | Severity | Root Cause / Evidence | Mitigation Strategy |
| :--- | :--- | :--- | :--- |
| **Reserved Word: `users`** | **Medium** | `users` is a reserved keyword in some SQL dialects (and sometimes quoted in PostgreSQL). | PostgreSQL natively allows `CREATE TABLE users`. Entity specifies `@Table(name = "users")`. Verified safe in PostgreSQL 15, but migrations should ensure consistent case. |
| **Enum Case & Type Discrepancy** | **Medium** | JPA uses `EnumType.STRING`. If PostgreSQL custom enum types were used, migrations would require `CREATE TYPE ...`. | Use standard `VARCHAR(20)` in Flyway with optional `CHECK (role IN ('USER', 'ADMIN'))`. Matches JPA `EnumType.STRING` perfectly. |
| **Timestamp Precision Divergence** | **Low** | Java `Instant` has nanosecond resolution; PostgreSQL `TIMESTAMPTZ(6)` has microsecond resolution. | Specify `TIMESTAMPTZ(6)` in Flyway DDL to match Hibernate 6's default mapping for Java `Instant`. |
| **Foreign Key Deletion Order** | **High** | `jobs` references `datasets(id)`; `datasets` references `users(id)`. | Enforce strict table creation order in Flyway: `users` -> `datasets` -> `jobs`. In tests, ensure `@BeforeEach` deletes in reverse order (`jobs` -> `datasets` -> `users`), which is already implemented. |
| **Local Developer Without Docker** | **Medium** | Developer runs tests on a machine without Docker running. | Document requirement: Docker must be running for `./mvnw test`. Alternatively, allow fallback to local PostgreSQL via properties if Docker is absent. |
| **Windows Batch Wrapper Stack Overflow** | **Low** | `mvnw.cmd` recursion issue observed on Windows command line when `MAVEN_BASEDIR` is unset. | Document execution command using `./mvnw` (PowerShell / Git Bash) or set explicit `MAVEN_BASEDIR` in documentation. |

## 12. Open Decisions & Recommendations

1. **Docker Compose Profile:**
   * *Finding:* `docker-compose.yml` does not currently specify `SPRING_PROFILES_ACTIVE`.
   * *Recommendation:* Add `SPRING_PROFILES_ACTIVE=prod` (or keep `local` with `ddl-auto=validate`) once Flyway is present, ensuring Docker Compose uses the migration path.
2. **Check Constraint on Progress:**
   * *Finding:* `Job.progress` has `@Min(0)` and `@Max(100)` in Java, but Hibernate DDL does not generate check constraints by default without specific validator integration.
   * *Recommendation:* Include `CHECK (progress >= 0 AND progress <= 100)` directly in `V1__initial_schema.sql`. Hibernate `validate` will pass and the database will enforce integrity.

* In `application-prod.properties`, `spring.jpa.hibernate.ddl-auto=validate` is configured.
* In `application-local.properties`, `spring.jpa.hibernate.ddl-auto=update` is configured.
* In `application-test.properties`, `create-drop` against in-memory H2 is configured.
* `pom.xml` has `com.h2database:h2` in test scope and no Flyway or Testcontainers dependencies.
* `docker-compose.yml` uses `postgres:15-alpine`.
* All 8 database integration tests implement `@BeforeEach` cleanup in strict FK dependency order (`jobRepository` -> `datasetRepository` -> `userRepository`).

### INFERRED (Reasonable Conclusions from Architecture)
* Testcontainers `postgres:15-alpine` with a shared singleton container will run within ~15–20 seconds total for the entire test suite on developer hardware and GitHub Actions.
* Setting `spring.jpa.hibernate.ddl-auto=validate` with Flyway migrations will permanently eliminate schema drift between development and production.
